Sour's dma_irq_test -- how many instructions run after a DMA before the
interrupt is taken.  19 readings, all of which this emulator now matches.

Two of them appear not to.  Its README gives $FFFF for both "SEI+INC" rows
and this reads $00FF.  The cartridge's own source settles it:

    setaxy8
    lda valueOnIrq          ; the byte the test left, $FF
    sta testResults, x      ; low byte
    inx
    stz testResults, x      ; high byte, zeroed on purpose

The high byte is written as zero every time, so the built cartridge cannot
print $FFFF for any emulator or for hardware.  The README's changelog says
its tests were changed after it was written; those two lines were not.

Recorded because the next person to read that table will see two failures
that are not there, and because it is worth having one case written down
where the published answer was the thing that was wrong.

tukuyomi's bsnes tests -- test_irq.smc, test_irq4200.smc, test_nmi.smc,
demo_irqtest.smc.  All four end red.  Red is failure: the last thing each of
them does is

    LDA $00 : CMP #$01 : BEQ pass : JMP fail
    pass:  backdrop $7C00 (blue),  STP
    fail:  backdrop $001F (red),   STP

so the whole verdict is one byte against one, and the screen colour is the
report.  Nothing in the collection says so; it was read out of the ROM.

What the byte is: their interrupt handler is

    PHA : PHY : LDA $4211 : LDY #$0000 : LDA ($05,S),Y : STA $00 : RTI

-- it reaches past its own pushes into the frame the interrupt made, and
records a byte from where the interrupt landed.  The cartridge then delays a
cycle-counted amount through a routine at $02:807D and asks whether the
interrupt arrived at the exact byte it aimed for.

This records $EA, the NOP that fills the delay, where hardware records $01.
The interrupt is arriving at a different instruction: not late by a line or
by a frame, but by a byte or two within one.

Measured before and after the H-timer change of this session: $EA both
times.  That change neither caused this nor fixed it, and saying so is the
point of writing it down.  This is a single-instruction interrupt-latency
question and it is still open.

Measured while chasing the four red screens above, and recorded because the
measurement is worth more than the conclusion I did not reach.

test_irq's first gate wants the byte at the interrupted address to be $18,
the CLC at $80E0.  This delivers $EA, the NOP one byte earlier.  Delaying
the interrupt line by a swept constant moves it: at +24 master cycles --
six dots, four processor cycles -- the byte becomes $18 and that gate
passes.

That is not the answer.  With +24 in place all four screens are still red,
so the gates further on fail for their own reasons, and dma_irq_test reads
19/19 at every offset from -24 to +40, so it does not constrain the
constant at all.  A number that satisfies one reading out of six is not a
measurement of anything; it is the shape of the first gate.

The likelier story, untested: these cartridges align the processor with a
cycle-counted delay at $02:807D before letting the interrupt in, so the
same four cycles could be the delay running short rather than the
interrupt arriving early.  That would put the fault in instruction timing,
where the delay is, and not in the interrupt at all -- and it would explain
why moving the interrupt fixes one gate and no others.

Whoever picks this up: sweep the offset again after any instruction-timing
change, and treat +24 as a symptom rather than a value to adopt.

Super Mario Kart -- the flat track, and what it is not.

The course renders as two plain slabs of colour, grey over tan, with the
sky, the karts, the HUD and every menu correct around them.  I have been
saying the DSP-1's guessed geometry was behind it.  It is not.

Driven into a race and measured there:

  * the Mode 7 matrix is zero.  A=B=C=D=0 for the whole frame, which maps
    every screen pixel to one place in VRAM -- exactly one flat colour per
    region, which is what the picture shows.
  * nothing writes $211B-$211E.  Not the processor, in a whole frame of
    bus records, and not any HDMA channel.
  * the DSP-1 is barely involved.  Over a race it is asked for command $06
    (project an object) 10,244 times and command $0A (the raster
    coefficients) twice.  Its guessed geometry cannot be drawing the road
    because the game is not asking it to.  $06 is how the other karts are
    placed on screen, and they are placed correctly.
  * HDMA is enabled with $FE -- channels 1 to 7 -- and channels 1 to 4 are
    configured exactly as they should be: indirect, two bytes to one
    register, feeding $211B, $211C, $211D and $211E.  Channel 5 drives
    $2105 for the mid-screen mode change and channel 7 the window.  The
    transfers run: the line counters advance through the frame.

  * the data they fetch is not there.  Each channel's table in WRAM is
    well formed and its pointers are followed correctly -- $4000 plus two
    bytes a line reaches $40A2 exactly as it should -- but the buffers
    those pointers name, $7E:4000, $7E:D000, $7E:6FE2, $7E:A0A2, read
    $FF from end to end.  Nothing writes them: zero writes into
    $7E:4000-$4FFF across five frames of bus records.

So the chain is: the game never fills its per-line matrix buffers, so
HDMA faithfully delivers unwritten memory, so the matrix is $FFFF or
zero, so every pixel of the road samples one place and the road is a
slab.  The question is what should be filling those buffers and why it
is not reached, and it is not the DSP-1: the raster command that would
be the obvious candidate is asked for twice in a whole race.

CORRECTION.  An earlier version of this entry said all seven channels
pointed at $210C.  That was wrong, and wrong in an instructive way: I
read the channel registers through Bus.read(), which resolves by page
kind, and the register file is not a page -- so every one of those reads
returned whatever the bus last carried, which was $0C, for all eight
channels alike.  A convincing, uniform, entirely fictitious answer.  I
had even "checked" it with a test program, which read the same registers
through the processor, where they work correctly -- so the check passed
and told me nothing about the reading I had actually taken.

There is a Bus.dma_channel() now that reads the file directly, and it
was written for exactly this reason.  The lesson worth keeping is
narrower than "verify your readings": it is that verifying a *different*
path than the one you used is not verification at all.

--- Mario Kart, what has been eliminated -------------------------------------

Independent of any input: the attract demo drives itself round a lap and
the road is the same slab, so the harness that presses buttons is not the
cause.

Ruled out, each by measurement:

  * the DSP-1.  Command $0A, the raster coefficients, is asked for twice
    in a race; command $06, which places the other karts, ten thousand
    times, and the karts are placed correctly.
  * the HDMA setup.  Channels 1 to 4 are configured exactly right --
    indirect, two bytes to one register, $211B through $211E -- and their
    line counters advance through the frame.
  * the tables.  Well formed, and their pointers are followed correctly:
    $4000 plus two bytes a line reaches $40A4 on the line it should.
  * VRAM.  The track is in there: 251 distinct tilemap bytes, 220 distinct
    tile bytes, 24,950 of 32,768 non-zero.  The picture the plane should
    be showing is present and complete.
  * Mode 7 rendering itself.  undisbeliever's four Mode 7 cartridges draw
    an identical detailed image through four different VMAIN routes, so
    the plane draws correctly when it is given a matrix.
  * the processor writing the buffers.  Zero writes into $7E:4000-$4FFF
    across five frames.
  * a bulk fill through the WRAM port.  Zero writes to $2180-$2183 in a
    frame, so they are not being filled by DMA either.

What is left: the buffers those channels read -- $7E:4000, $7E:D000,
$7E:6FE2, $7E:A0A2 -- are $FF from end to end, except for one byte at the
very start of the first, and nothing observed fills them.  Four distinct
(A, D) pairs do reach the matrix over a frame, including plausible ones
like -9325 and 50, so something writes it occasionally; the rest of the
lines get $FFFF from unwritten memory.

The next question is what fills those buffers on hardware, and it has to
be answered from the cartridge's own code rather than by guessing at the
emulator.  Everything above is elimination, which is worth having written
down: it is two sessions of work and none of it needs doing again.

BG3 and BG4 siblings.  Same image, same 32 colours, same 11,076 bytes of VRAM,

The divider has a during, and this does not model it.  Six failures found.

Fixing the screen reader turned 426 unreadable screens into 366, and with
them six cartridges that report failure where one did before:

  blargg_2010-03-14/speed_2_freezes2      Failed
  blargg_2010-03-14/test_timer_speed      0A 2731 / 1A          Failed
  blargg_2010-03-14/test_timer_speed2     0A 2731 / 1A 2731     Failed
  blargg_2010-03-14/test_timer_stop2      00                    Failed
  blargg_2010-03-14/timer_at_power_reset  FFD2                  Failed
  muldiv_tests/div_behavior   "WRDIVB write during div should reload
                               WRDIV into RDMPY"                Failed #6

The last one is the one with an answer attached, and the answer is in a
notes.txt beside the ROM, the same place the multiplier's was:

    WRDIVL write during divide has no effect on result.
    WRDIVH write during divide has no effect on result.
    WRDIVB write during divide reloads RDMPY with last written value to
    WRDIV (value written is ignored).
    Start divide: copy WRDIV to RDMPY.  Copy WRDIVB to internal right
    shifter.

So RDMPY is the divider's working register, and reloading it part way
changes the answer -- which is exactly what the cartridge measures.  Its
test 5 divides $A359 by $81 uninterrupted and wants $0144 remainder
$0015; test 6 interrupts it and wants $017F remainder $839A.

A sixteen-step restoring division reproduces both: the first exactly, the
second when the reload lands before the tenth step, which is where three
NOPs and a store put it.  Test 7's earlier store wants $0111 remainder
$001E, and that is steps eight and nine.  Three numbers, one algorithm,
no fitting.

What is missing is the cadence.  Implemented at six master cycles a step,
the reload landed on step twelve; at eight and at four it still failed at
test 6, and at twelve it failed earlier, at test 2.  div_timing.smc
prints the intermediate RDDIV and RDMPY at every cycle from $02 to $11
and ours are wrong throughout even though the final $1855 remainder $0002
is right -- our quotient gains two bits at some cycles and none at
others, which is a divider running at a rate the cartridge does not
recognise.

The stepped divider is reverted.  It passed nothing the instant one did
not, and its timing was invented.  The algorithm above is worth keeping,
and so is div_timing's table: sixteen rows of what the intermediates
should be, which is enough to settle the cadence for whoever picks this
up with more patience than I had left today.

$F0's upper bits: known, verified, and deliberately not implemented.

Four of the six newly-visible failures are blargg's SPC700 timer tests,
and his own working notes sit beside the ROMs.  They are a table of
measurements against $F0 values:

    0A 2731   1A 1639   2A  910   3A  482
    4A 2049   5A 1366   6A  819   7A  455
    CA  819   DA  683   EA  512   FA  342

and a formula worked out from them:

    divisor = 1 + (1 << clock_speed) + (15 >> (3 - timer_speed))
      clock_speed = $F0 bits 6-7,  timer_speed = bits 4-5
    -> { 3, 5, 9, 17 ; 4, 6, 10, 18 ; 6, 8, 12, 20 ; 10, 12, 16, 24 }

Checked against every measured count: 2731x3, 1639x5, 910x9, 482x17,
2049x4, 1366x6, 819x10, 455x18, 819x10, 683x12, 512x16, 342x24 all come
to about 8192.  Twelve values, one formula, no fitting.

This emulator implements $F0 bits 0 to 3 -- timers off, RAM read-only,
RAM unmapped, timers enabled -- and ignores 4 to 7 entirely.  The screen
of test_timer_speed says so exactly: "0A 2731" is right and "1A" is where
it stops.

Not implemented, on purpose.  Those bits stretch the SPC700's own clock,
so the processor, the DSP and all three timers slow together, and that is
the synchronisation between the sound chip and the console -- the part
that currently passes all eight of blargg's audio cartridges and tracks a
real game's music at 0.983.  Against that: no commercial game writes
those bits.  $F0 is the test register.

So the trade is two to four test cartridges against the riskiest timing
in the emulator, for behaviour no game uses.  Written down with the
formula and the place it would go -- APU.tick, where the SPC700's cycles
become the timers' scaler input -- so that whoever decides differently
starts from the answer rather than from the measurements.

The multiplier's start, settled; the divider's, not.

With the unit stepping once a processor cycle, three of the four muldiv
cartridges pass: div_behavior, mul_behavior, and mul_timing -- the last
against a checksum over its whole sixteen-row table, which no accident
matches.  It wants one cycle between the write that starts a multiply and
its first step.

The divider's is not a delay.  Sweeping it from nought to eight only
slides its table along; the values themselves are wrong.  Ours reaches a
quotient of $0001 four steps in, which for $AA55 over $07 means the first
three comparisons all failed, and they should -- $07 shifted up fifteen,
fourteen and thirteen places are all larger than $AA55.  So the shape is
right and the alignment is not, and whatever is missing is in how the
first step relates to the write rather than in how many clocks apart the
steps are.

Left there.  div_timing is the only one of the four still failing, and it
is failing on less than it was.

Three of the four, and where the fourth disagrees.

RDDIV is not cleared when a division starts.  The notes say what is
loaded -- WRDIV into RDMPY, WRDIVB into the shifter -- and say nothing
about the quotient register, and div_timing deliberately leaves $FFFF
there before every reading, which is only worth doing if what happens to
it is the thing being watched.  It shifts out as the quotient shifts in:
FFF8, FFF1, FFE3, FFC6, FF8C, ... 8C2A, 1855.

With that, and one processor cycle between the write and the first step:

  mul_behavior  PASSED
  mul_timing    PASSED   (checksum over its whole table)
  div_behavior  PASSED   with no delay on the divider
  div_timing    PASSED   with a delay of one

-- and those last two are the same number set differently.  div_timing
wants the whole table one step later; div_behavior wants the reload that
a mid-division write causes to land after the tenth step, and a delay of
one puts it after the ninth.  Latching the reload to the next step does
not bridge it: that moves it to where it already was.

So a single "cycles before the first step" cannot satisfy both, and the
difference between them is one step in where a write lands relative to
the run.  Something distinguishes the write that starts a division from
the write that interrupts one, and neither notes.txt nor these four
cartridges say what.

Left at no delay, which is the setting that keeps three passing.
div_timing is the one that fails, and it fails by one step.

Ladida's HDMA cartridge: one fault found under another.

It drew nothing at all, and the reason was not HDMA.  CGWSEL's force-black
field had inside and outside swapped, so a cartridge asking for "black
inside the colour window" with no window set had its whole screen blacked.
Fixing that also fixed two of undisbeliever's window cartridges, which
nothing was aiming at.  The colour window was painting over the thing this
ROM is actually about.

What it is about, from byuu's own account beside the ROM: HDMA's
initialisation at the top of a frame raises the transfer flag for all eight
channels, including disabled ones, and then fetches a line counter only for
the enabled ones.  So a channel switched on part way through a frame still
carries that flag and transfers without a line fetch, reading its table one
entry out.  And when no channel is enabled at the top of the frame the
initialisation does not run at all, the flag stays down, and switching one
on later costs a scanline before the first transfer.  The first case makes
the picture green with no white line; the second puts the white line in.

The real machine's answer is in expected-result.webm, a photograph of a
CRT: white above, a black rectangle in the middle, green across the bottom
third.

This now draws white with a single black line where the green should
start.  The boundary is in the right place and the green is missing, so
the transfers stop after one.  The cartridge writes its line counter
straight into $430A and then enables the channel mid-frame, which is the
whole trick, and the window in which $420C is set is short enough that
sampling the state has not caught it yet.

Left there.  The flag is raised for all channels at init now, which is
half of byuu's description; the other half is what happens on the very
next HBlank, and that is where to start.

Ladida's cartridge: solved, against the photograph.

Three faults, each hiding the next.

The first was that a channel switched on part way through a frame never ran
at all.  hdma_run gated on a flag set only by a line-counter reload, and
reloads only happen at the top of a frame for channels already enabled --
so the one thing this cartridge does was the one thing that could not
happen.  The flag is not "has a table", it is "has not terminated", and
nothing has terminated at power-on.

The second was that termination was remembered across frames with nothing
to clear it.  On the hardware there is no such latch: a channel is finished
because its line counter is zero, and writing a count to $43xA is enough to
revive it.  The cartridge writes $01 there immediately before enabling,
every frame, which is exactly what that write is for.  Without this it drew
correctly on one frame and never again.

The third was the reset value of DoTransfer, which byuu published as
cleared and marked "this is now under debate, may not be necessary".
Cleared is wrong.  A channel first used part way through a frame then
spends its first HBlank fetching a line counter, and every read after that
is one byte along: the four data bytes come from 00 00 1F 00 instead of
08 00 00 1F, which is colour $001F rather than $1F00 -- red rather than
green, and repeated down the screen as a gradient because the channel
survives instead of ending.  byuu's own note beside the ROM says the right
answer is "no extra white line, and the color is green instead of a red
gradient", and the photograph agrees.  So the flag is set at reset, and a
reload raises it whatever count it read.

What draws now: white above, green across the bottom third, boundary in
the right place.  What does not: the black rectangle in the middle of the
white area, which is nothing to do with HDMA.  That is next.

A test in the suite had asserted the opposite of all this -- that a
mid-frame enable does nothing until the next frame.  It was reasoning
written down as fact, it had never been checked against anything, and it
passed for as long as the emulator was wrong in the same way.  Rewritten
to the cartridge's own sequence.

Correction to the entry above, and the rest of Ladida.

That entry said the reset value of DoTransfer should be set rather than
cleared, on the strength of the cartridge drawing green.  That was wrong,
and wrong in the way worth recording: the reference is a video, not a
photograph, and it shows the cartridge in two states.  A still frame taken
out of it is not "the answer" -- it is one of two answers, and I had
matched the emulator to whichever one I happened to have extracted.

The cartridge is a demonstration of both halves of byuu's paragraph, and
B switches between them.  Pressing it toggles a byte that does two things:
it enables channel 7 at the top of the frame, whose only purpose is to make
the init pass run at all, and it switches the colour window on.  So:

  button up    no channel enabled at the frame's start, init skipped,
               DoTransfer clear, the mid-frame channel fetches a line
               counter first and reads its table one byte along -- colour
               $001F, a red gradient, with the extra white line
  button down  init runs, raises DoTransfer for all eight, the mid-frame
               channel transfers without fetching -- colour $1F00, green,
               no extra white line, and the black rectangle appears

Both are correct hardware behaviour.  An emulator has to draw red for one
and green for the other, and drawing green for both -- which is what the
raised reset value did -- is not a fix, it is the same fault with a
different picture.  byuu's published reset value is right.

The rectangle is the colour window: HDMA channel 7 writes WH0/WH1 a line
at a time from a table, so the bounds are (64,192) on lines 49 to 128 and
empty elsewhere, and CGWSEL's force-black paints inside it.  Nothing on the
main screen at all -- every dot of that screen is the backdrop, and the
clip applies to the backdrop like any other colour.  That last part now has
a test of its own, because it is the part an emulator is most likely to get
wrong by only clipping layers.

Two more things worth keeping.  The first: I read a rendered PNG as RGBA
when this emulator's framebuffer is BGRA, called a red gradient blue, and
built an argument about byte-swapped colour on top of it.  The framebuffer
order is in tools/contactsheet.py and I had not looked.  The second: I
looked at a contact sheet from before a rebuild and concluded the black
rectangle was missing, when it had already been drawing.  Both times the
correction came from reading pixel values instead of looking at a picture.

tukuyomi's four interrupt cartridges: the mechanism, not the constant.

The note further up recorded that delaying the interrupt line by a swept
+24 master cycles moved test_irq's first gate from $EA to the $18 it wants,
and rejected it: a number that satisfies one reading out of six is the
shape of that reading, not a measurement.  That was right to reject.  What
was missing was where the four cycles actually are.

Measured, with a new record of when the line goes up:

  02:80DE  SEC   starts 1736364, opcode fetch 8, internal cycle 6
  the line rises at                1736372
  the instruction ends at          1736378

So the line rose exactly at the start of the instruction's last cycle, and
this emulator took the interrupt at the end of that instruction.  The
cartridges say it should not have: they aim an interrupt at a chosen byte
with a cycle-counted delay and report the byte it landed on, and all four
report one instruction earlier than the console does.

The poll was at the instruction boundary.  It now requires the line to have
been up before the last cycle began -- a line that rises inside that cycle
waits for the end of the next instruction.  With that, test_irq's first
gate reads $18.

Two guards, both from hardware.  Sour's dma_irq_test reads 13 of 14 before
and after, the one mismatch being the row its own README gets wrong (noted
further up).  The twenty unit-test modules pass.

The four screens are still red: the gates after the first fail for their
own reasons, exactly as they did with the fitted constant in place.  What
is different is that this is a mechanism with a measurement behind it
rather than a number chosen to make one gate pass, so the gates that
remain can now be read as their own questions.

A test in this session's HDMA work failed on this change and was fragile,
not wrong: it let an interrupt in on the first frame of all, before the
program had finished writing its tables, so a channel could be armed
pointing at whatever RAM held.  It now waits two frames.  Worth recording
because the change that exposed it had nothing to do with HDMA -- a test
that depends on power-on RAM will eventually fail for a reason from the
other side of the emulator.

The same rule for NMI, and a better way to read these four cartridges.

Disassembling test_irq from a correct instruction boundary shows what the
screen colour was hiding.  Each gate is:

    JSL $02807D            cycle-counted delay
    SEP #$20 / SEC / NOP / CLC      the landing zone
    LDA $00                the byte the handler recorded
    CMP #$18               gate 1 wants the CLC
    BEQ next
    STA $700001            failure: the wrong byte, into SRAM
    JMP report
  next:
    LDA $700000 / INC A / STA $700000     a count of gates passed

So $70:0000 counts the gates that passed and $70:0001 holds the byte the
failing one saw.  A red screen says "somewhere"; these say where and what.
Reading them is two lines and should have been the first thing done to
these four cartridges rather than the last.

Before the poll change, with the byte read only through the screen:

  test_irq       1 gate,  saw $EA        test_nmi   0 gates, saw $EA

After it, and after giving NMI the same rule -- it is latched on an edge
rather than held as a level, but the processor looks for it at the same
moment:

  test_irq       2 gates, saw $18        test_nmi   2 gates, saw $18
  test_irq4200   no count written        demo_irqtest  3 gates

Gate 1 wants the CLC at $80E0 and gate 2 wants the NOP one byte before it,
with a shorter delay.  Both pass now.  Gate 3 is where both stop, and both

Guards unchanged: dma_irq_test 13 of 14 with only its own README's bad row

Correction, and where test_irq actually stops.

The entry above says both cartridges stop at gate 3.  They stop at gate 2.
The counter at $70:0000 is not zero when the first gate runs, so reading it
as a count of gates passed is off by one, and the failure recorder can be
found properly instead: the only STA-long in bank 0 that runs on the way to
the report is at $8138, which is gate 2's.

Gate 1 wants the CLC at $80E0 and passes.  Gate 2 has the same landing zone
one delay further on and wants the NOP before it, and gets the CLC.

Traced through both landing zones:

  gate 1   00:80DC SEP  clock 1736342 +22
           00:80DE SEC        1736364 +14
           00:80DF NOP        1736378 +74   -> handler
           00:80E0 CLC        1736798

  gate 2   00:812D SEP  clock 2451076 +22
           00:812F SEC        2451098 +14
           00:8130 NOP        2451112 +74   -> handler
           00:8131 CLC        2451532

Identical.  The interrupt is taken at the end of the NOP in both, so both
record the byte after it.  On the console the two differ by one
instruction: gate 1 lands at the end of the NOP and gate 2 at the end of
the SEC.

That is the shape of the remaining fault and it is not the poll rule --
the poll rule is what makes gate 1 right.  Between the two gates the
program changes only how long it waits, so what has to be wrong is the
length of that wait: the cycle-counted delay at $02:807D with a different
argument, or the re-arming of the V-timer by the write to $4200 that sits
between them.  Both are measurable and neither has been measured yet.

Worth saying plainly: the earlier reading of "one instruction early" was
right about the poll and wrong to stop there.  Two faults were stacked, one
in when the processor looks and one in how long the program waits, and
fixing the first moved the failure from gate 1 to gate 2 rather than
turning the screen blue.

What the delay routine actually is, and why gate 1 passing is not evidence.

$02:8000 is not a delay at all.  It waits for the field flag and V-blank,
then latches the H counter through $2137 and reads it back from $213C twice,
subtracts, and computes a delay from the difference -- the program aligns
itself to a dot before every gate.  The delay it computes is then spent in
$02:807D, which subtracts $140, loops subtracting $64 while the value is
still $100 or more, subtracts $9C, puts what is left in X and jumps through
a table at $842A.

The table entries are chains built to be two master cycles apart:

    XBA + BIT #imm     20 + 16 = 36     (three cycles and two, all from ROM)
    LDA dp + NOP       24 + 14 = 38     (three cycles, one of them WRAM)

Swapping one pair for the other buys exactly two master cycles, which is the
finest step the console offers -- there is no instruction that costs less
than a whole cycle, so the routine trades cycle counts against memory speeds
instead.  Measured here, gate 1 takes the chain at $02:823A for 234 master
cycles and gate 2 the one at $02:824C for 236.  Both correct, and the two
gates are two master cycles apart by design.

Which is the problem.  Both gates were landing at exactly the same offset
into the SEC -- eight master cycles, the start of its last cycle -- and two
cycles of difference had gone missing.  It had not: irq_rose_at was
recording when the timer event was *processed*, and events are processed at
the end of whichever processor cycle crossed their deadline.  That rounds
the instant up to a cycle boundary, and the processor's decision compares it
against a cycle boundary, so the rounding threw the whole question away.
Both gates rounded to the same boundary.

Recording the real instant instead -- the event's own deadline -- puts gate
1's rise at one master cycle into the SEC rather than eight, and gate 1
fails.  So gate 1 was passing because the rounding happened to land it on
the boundary it was being compared against.  That is not a pass and must not
be read as one.  The commit that claimed it should be read with this beside
it.

The change is reverted, because shipping a cartridge regression on the
strength of a half-finished investigation is worse than leaving a known
artefact in place with a note on it.  What the measurement leaves behind is
a well-posed question that neither the poll rule nor the delay chains can
answer: the V-timer's interrupt fires about seven master cycles earlier,
relative to where the program has aligned itself, than this cartridge
expects.  Seven is not a multiple of four, so it is not a whole dot, and
either the alignment this ROM computes from $213C is landing somewhere
slightly different here or the timer's instant is.  Both are measurable.

A whole class of explanations eliminated, by sweeping a knob that should not
be shipped.

The question left above was whether the alignment this cartridge computes
from $213C lands somewhere slightly different here, or whether the timer's
instant does.  A skew was added to the counter a $2137 read reports, purely
to sweep it, and the two cartridges read at each setting.

With the rounded rise time -- what is shipped:

    skew  -12 .. -4   irq $EA   nmi $EA
    skew   -2 .. +6   irq $18   nmi $18
    skew  +10 .. +14  irq $A5   nmi $A5

With the real rise time:

    skew   -8 .. +3   irq $EA
    skew   +4 .. +12  irq $18

No setting passes both gates, either way.  The recorded byte walks whole
instructions -- $EA, then $18, then the LDA after it -- and gate 1 and gate 2
change together.  They never sit on opposite sides of the decision.

That is a real elimination, and it is the point of writing it down.  The
counter a $2137 read reports is a dot, so any constant added to it moves the
program's arrival in steps of four master cycles; the two gates are two
apart by construction; a four-cycle step cannot separate a two-cycle pair.
So no error of the form "this emulator's H counter is N dots out" can
explain these two gates, however N is chosen.  Every version of that idea is
now dead, including the one the entry above named as likely.

What survives: the cartridge resolves its own sub-dot phase by latching the
counter twice, 230 master cycles apart, and testing whether the reported
difference came out 57 dots or 58 -- 230 is 57.5 dots, so the answer depends
on the phase, and the program adds 0 or 2 master cycles accordingly.
Measured here, both answers do occur.  Whether they occur on the same phases
the console gives is the question that is left, and it is a two-cycle
question about the counter's phase rather than a four-cycle one about its
value.  A knob on the reported dot cannot reach it, which is why the sweep
above could not have succeeded and why the knob is not in the tree.

Soaking eight titles, and a finding that turned out to be the opposite.

Eight games from the library, twenty thousand frames each -- five and a half
minutes of play apiece -- with pseudo-random input, covering plain LoROM and
HiROM, two SA-1 titles, CX4, SuperFX and DSP.  All eight ran to the end
without a crash or a hang, and seven finished with a full screen: between
85,000 and 113,000 non-black pixels.

The eighth, Rockman X2, ended with 3,960, and what it was drawing is the
cartridge's own CX4 test:

    INTERFACE REGISTER    ERROR!
    REGISTER FILE         ERROR!
    DATA RAM              ERROR!

Three named failures from a program written by the people who made the chip
-- the same kind of evidence as the SPC7110's ALL OK, and it looked like the
best target of the day.

The reference settles what the chip is: a Hitachi HG51B169, whose *program*
is paged out of the cartridge ROM but whose lookup tables are a 1024 by
24-bit ROM inside the package.  So the three failing lines are all about
memory the console addresses directly -- data RAM at $6000-$6BFF, registers
at $7F40-$7FAF -- and none of them needs the tables.  That is implementable
here.

It was implemented, and it was wrong.  With those addresses answering, the
game stops printing the diagnostic and goes black: it runs further, into
bank $00 and seventy-seven addresses rather than forty-five, and then waits
for a calculation that cannot come.

Which means the diagnostic was never a report about this emulator's CX4.  It
was the game correctly noticing there is no CX4, and printing so.  Making
those addresses answer did not fix anything; it removed an accurate reading
and left a black screen in its place, and a chip that answers reads out of
RAM is exactly the guessing-from-effects this project refuses elsewhere.

Reverted.  Rockman X2 says ERROR three times again, which is the truth.
The entry that says these chips are out of reach without their dumps was
right, and the only thing worth adding to it is that the CX4 is out of reach
for the tables rather than for the program.

Sources: https://wiki.superfamicom.org/capcom-cx4-hitachi-hg51b169

test_irq, measured to the point where the two gates should separate.

The last entry eliminated every explanation of the form "the H counter is N
dots out".  What was never measured was the other side: where gate 2's
interrupt actually lands.  It could not be, because with the real rise
instant gate 1 fails and the program never reaches gate 2.  Adding a
constant to the instant the processor decides against -- a measurement
build, not a change -- gets past gate 1 and lets both be read.

    gate 1   SEC starts 1736364, the rise lands at +9
    gate 2   SEC starts 2451098, the rise lands at +9

Identical.  The design wants them two apart: gate 1's interrupt deferred to
the NOP, gate 2's taken at the end of the SEC.

The two apart are in the program, and they arrive:

    gate 1   JSL $02807D with A=$899A ... 36390 master to the SEC
    gate 2   JSL $02807D with A=$899C ... 36392 master to the SEC

So the program reaches its landing zone two cycles later for gate 2, exactly
as written, and the interrupt lands at the same offset anyway -- which means
the interrupt moved two as well.

The alignment explains why the rest cancels and this does not.  $02:8000
reads the H counter twice, works out where it is, and computes a delay so
that start plus delay is a constant; gate 1 starts at position $013A with a
phase correction of 2, gate 2 at $0130 with a correction of 0, and their
delays differ by exactly the ten that separates the positions.  That is the
routine doing its job.  The two from the explicit call afterwards is the
part that is meant to survive.

What cannot be right, whatever the cause: the two rise instants are 1736373
and 2451107, and 714734 between them is not a multiple of four.  A V-only
timer fires at the same dot of a line, lines are 1364 master and the two
that are not are 1360 and 1368, so any two firings must be a whole number of
dots apart.

`_arm_irq` has one path that can produce an instant off the dot grid:

    if at <= self.master_clock:
        at = self.master_clock + 1

-- an arbitrary master cycle, wherever the processor happened to be, rather
than the next dot at which the comparison could be true.  That is the first
mechanism found that can put an interrupt where a console cannot, and it is
where to look next.  Not changed here: it wants its own measurement, and
this session's record already has one fix that was really a rounding
artefact wearing the right colour.

--------------------------------------------------------------------------------
The interrupt that landed off the dot grid.

The entry above named `at = self.master_clock + 1` in `_arm_irq` as the
first mechanism found that can put an interrupt where a console cannot, and
left it alone pending its own measurement.  Measured:

For a V-only match that path is not an edge case, it is every time.
`_arm_irq` runs while the line event is being processed, so `at = line_start`
has always just gone by, and the interrupt is placed one master cycle after
wherever the processor happened to be -- an instant with no relation to the
dot grid.  Two firings measured 714734 apart, which is not a multiple of
four, and no console can do that: the comparison is against a counter that
moves a dot at a time and every line is a whole number of dots.

Removing the clamp altogether puts it on the grid and loses gate 1 of
test_irq, which had been passing on the old behaviour.  That is the third
time in this session that a defensible change has taken away an accidental
pass, and the first time there was a third option: keep the clamp, and round
it up to the next dot at which the comparison could be true.

    at = self.master_clock + 1
    at += (-(at - line_start)) & 3

With that, everything holds at once:

    test_irq   $18, gate 1 passes        test_nmi   $18, gate 1 passes
    dma_irq_test  14 of 14               twenty test modules
    the library   76 of 76 unchanged

Same observable behaviour as before, one impossibility gone.  Worth saying
why that is different from the two reverts: those replaced an accidental
pass with an honest failure and gained nothing observable.  This one keeps
every reading and removes the thing that could not be true, which is the
shape a fix is supposed to have.

--------------------------------------------------------------------------------
Where the V match fires: eliminated too.

With the dot-grid fix in, gate 1 passes and the program reaches gate 2, so
both landing zones can be read without any measurement build.  Both rises
land at +8 into the SEC -- identical -- because what is recorded is the
rounded processing time, which quantises the two cycles apart.

Recording the real instant instead puts gate 1's rise at +4, one dot after
its SEC begins, and gate 1 wants +8 or later.  One dot short, which looked
like an answer.  It is not: with the clamp in place the computed instant
never survives, because for a V match it has always just gone by, so the
interrupt is placed wherever the clamp puts it whatever `at` said.

So the clamp was taken out of that path and the firing dot swept, with both
gates pinning it from opposite sides:

    dot 0, 1, 2     irq $EA      gate 1 fails
    dot 3, 4, 5     irq $18      gate 1 passes, gate 2 fails
    dot 6           irq $A5      past both

No dot satisfies both, and the reason is the same shape as the H counter
elimination: the gates are two master cycles apart by construction and a dot
is four, so a knob that moves in dots cannot put one on each side of a
boundary.  Every explanation of the form "the V timer fires N dots into the
line" is now dead as well, for any N.

What that leaves is genuinely narrow.  The two cycles are in the program and
they arrive -- 36390 against 36392 master to the landing zone.  The
interrupt instant, once it is not being decided by the clamp, is fixed to
the line and cannot move with the program.  So the difference must appear in
the comparison, which is between an instant on the dot grid and a boundary
on the processor's own clock -- and the only part of that this emulator does
not derive from first principles is `cycle_start`, the instant the current
processor cycle began.  That is the next thing to measure, and nothing else
is left to guess at.
